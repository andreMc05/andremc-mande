**Core web platform APIs are sufficient for complex, high-performance interactive applications — including games — without frameworks or external libraries.** That choice removes framework runtime overhead, large bundles, transitive dependency risk, and ongoing migration costs.

[Bee Brave](/projects/bee-brave-pure-code) (a top-down arcade shooter with bee AI, hive cell building, resource harvesting, combat, particles, parallax, and screen shake) was built as a pure ES-modules Canvas project with no bundler or dependencies to test exactly this claim. You can [play it](https://andremc05.github.io/bee-brave-pure-code/) or read the [architecture](https://github.com/andreMc05/bee-brave-pure-code/blob/main/dev-knowledge/architecture.md), [performance](https://github.com/andreMc05/bee-brave-pure-code/blob/main/dev-knowledge/rules/performance.md), and [rendering](https://github.com/andreMc05/bee-brave-pure-code/blob/main/dev-knowledge/rendering.md) docs. They record standard high-performance patterns implemented directly against the platform.

## File size and payload

Framework and engine runtimes add fixed costs before any application logic. Recent SPA comparisons show basic React apps in the ~58 KB uncompressed / ~19 KB Brotli range, Vue smaller, and Angular larger; medium and complex SPAs grow further with state and data libraries. Phaser (a popular HTML5 game framework) ships a full minified and gzipped build around 345–347 KB; even aggressive custom builds (removing unused physics, renderers, and so on) typically stay well above 100 KB.

Vanilla ES modules ship only the code you write. Native browser loading of modules means no bundler tax and no unused framework code. For a game that already needs pools, spatial hashing, culling, and offscreen caching, that difference is pure overhead.

## Security and hidden code

Supply-chain risk is dominated by the npm ecosystem. Sonatype tracking shows cumulative malicious packages approaching or exceeding 1.2 million by the end of 2025 and nearly 2 million by late 2026, with the large majority (often 89–99% in recent quarters) on npm. New malicious packages numbered in the hundreds of thousands annually; self-propagating worms (for example, Shai-Hulud) and credential-stealing campaigns have compromised hundreds of packages at a time.

Independent analyses consistently find that the large majority of open-source vulnerabilities live in transitive (indirect) dependencies — figures in the 75–95% range appear across Snyk and Endor Labs reports. A zero-dependency pure-ES-modules codebase has none of this surface: no install scripts, no transitive packages, no lockfile surprises, and no hidden functionality beyond what the browser platform itself provides. The only external code is the heavily audited browser implementation of Canvas, `requestAnimationFrame`, Web Audio, `localStorage`, and the rest.

## Maintenance

Browser APIs are deliberately stable and backward-compatible over multi-year horizons. Framework major versions routinely require migrations (component models, hooks, reactivity systems, build tooling). A pure Canvas and ES-modules game stays on the same language and platform APIs. The [architecture rules](https://github.com/andreMc05/bee-brave-pure-code/blob/main/dev-knowledge/rules/architecture.md) already encode the necessary discipline: movement scaled by `dt * 0.06`, millisecond timers subtracting `dt` directly, update/draw separation, `ObjectPool` plus `SpatialHash`, and visibility culling. There is no dependency update treadmill and no “this abstraction is deprecated.”

## Performance

HTML5 Canvas is an immediate-mode drawing surface. There is no virtual DOM reconciliation, no component tree, and no framework runtime on the hot path. Google’s long-standing Canvas performance guidance (web.dev) recommends exactly the techniques in the Bee Brave [rendering](https://github.com/andreMc05/bee-brave-pure-code/blob/main/dev-knowledge/rendering.md) and [performance](https://github.com/andreMc05/bee-brave-pure-code/blob/main/dev-knowledge/rules/performance.md) docs: pre-render repeated or expensive content to off-screen canvases, batch similar draw calls, minimize state changes, cull off-screen entities, use `requestAnimationFrame` with delta-time, and cache gradients and paths.

Modern browsers hardware-accelerate Canvas. 60 FPS is the conventional target and is routinely achieved for 2D games when those patterns are followed. Studies comparing animation technologies show Canvas (and WebGL) scaling to far higher object counts than DOM or SVG approaches before frame-rate collapse. The game’s architecture — pools, a spatial hash for neighbor queries, dirty-flag parallax, visibility helpers — is a direct implementation of those platform-level practices.

## Why a game is a strong test

A top-down shooter with swarm AI, dynamic hive construction, a resource economy, multiple weapon types, particles, and layered rendering exercises many domains at once: simulation, collision, rendering, input, audio, persistence, and UI. Keeping all of them interactive and performant without an engine or framework is non-trivial.

The pure-ES-modules implementation, together with its explicit performance rules (pools, spatial queries, culling, off-screen caching, no per-frame DOM queries), shows that the platform primitives are adequate. AI-assisted coding in 2024 and later further lowers the cost of writing those systems directly, because the code remains plain JavaScript that models understand without framework-specific idioms.

## In short

The web platform already supplies the necessary building blocks: Canvas 2D, `requestAnimationFrame`, ES modules, Web Audio, storage, and pointer events. Frameworks and libraries add convenience and structure at the cost of bytes, attack surface, and long-term maintenance. For workloads that can be expressed as a simulation plus an immediate-mode render loop, that cost is optional.

Bee Brave is concrete evidence that a non-trivial interactive application can be built and kept performant entirely within those platform boundaries.
